# Predictive Maintenance Intelligence Platform

A Streamlit decision-support app, not just a classifier: upload a CSV of
current asset readings and it validates the data, estimates failure risk,
explains *why* each alert fired, tracks its own performance over time, and
lets you drill into any single asset's history.

| Tab | What it does |
|---|---|
| 🔍 **Predict & Alert** | Upload a CSV → data-quality check → recommended maintenance type (with confidence), failure-risk score + tier (Low/Medium/High/Critical) + recommended action, remaining useful life, next due date. |
| 🧠 **Explain a Prediction** | Pick any asset from the last batch and see which readings pushed its risk score up or down - real SHAP values when available, a transparent fallback otherwise. |
| 📊 **Investigate Asset** | Trend charts and full history for one asset, built from everything predicted through this app so far. |
| 📈 **Model Performance** | Training-time accuracy/MAE/R² and feature importance, this session's usage stats, a data-drift check of the latest upload against the training distribution, and an optional feedback loop to score the model against real outcomes once they're known. |

Models are Random Forests trained on a synthetic dataset built to mirror this
plant's real shift maintenance reports - retrain on real historical
maintenance records once they're available (see **Retraining** below).

## Folder contents

```
app.py                  - the Streamlit app (UI only - wires up pm_logic.py)
pm_logic.py              - all the actual logic: validation, prediction, risk
                            tiering, explainability, drift checks, the
                            prediction log, and the actuals feedback loop.
                            No streamlit import, so it's unit-testable on
                            its own with plain python3.
requirements.txt        - pinned package versions
reference_stats.json    - training-data statistics used to validate/flag
                            uploaded rows (generated by train_models.py)
metrics_summary.json    - training-time accuracy/MAE/R² + feature
                            importance, shown in the Model Performance tab
sample_input.csv        - a ready-made file to test the upload with
```

There's no `models/` folder here on purpose - the 4 trained models (~27MB
total) are hosted on Google Drive instead of committed to Git, since GitHub's
web uploader rejects files that large. `app.py` downloads them into a local
`models/` folder automatically the first time it runs, using these file IDs:

| Model | Google Drive file |
|---|---|
| `maintenance_type_classifier.joblib` | `1yF-zgkKA_fX9qPkVeMRuAL6N9EafVlwL` |
| `failure_risk_regressor.joblib` | `1oNpbkDPf8W5LlWumroQlBWmHgiy6K0mo` |
| `rul_regressor.joblib` | `1BjAYSTWLqKSktTWri1mNzxSIF0mMHbcW` |
| `days_until_due_regressor.joblib` | `1wqk3O2bw_cTIZQw9leNhoTQ3NSv4ZxV9` |

`reference_stats.json` and `metrics_summary.json` are tiny (a few KB each),
so unlike the models they're committed straight into the repo next to
`app.py` - nothing to upload to Drive for those two.

**Before deploying, double-check all 4 model files' sharing setting is
"Anyone with the link" (Viewer).** If any one of them is still private, the
download will fail (or silently save an HTML "permission denied" page
instead of the real model, which then fails to load) - this is the single
most common thing that goes wrong with this setup, so check it first if the
app errors out.

## What's new vs. the original dashboard

1. **Input validation, not blind trust.** Every uploaded row is checked
   against what the models actually learned from (`reference_stats.json`):
   unseen categories (e.g. a `comp_type` that never appeared in training),
   readings outside the training range, missing values, and bad types are
   all flagged in a data-quality panel rather than silently mis-predicted or
   crashing the app. Missing numeric values are imputed with the training
   median; unseen categories are left for the model's own
   `handle_unknown="ignore"` encoding to absorb (it just has less signal for
   that row - the flag tells you so).
2. **Explainability.** The risk regressor's prediction for any single asset
   can be broken down into which readings pushed it up or down. This uses
   real SHAP (`TreeExplainer`, exact for a Random Forest) when the `shap`
   package is installed and working; if it isn't, `pm_logic.py` falls back
   automatically to a transparent heuristic (how far each reading sits from
   the training average, weighted by that feature's overall importance in
   the model) - same bar chart either way, with a caption saying which
   method produced it. **If `shap` fails to install on Streamlit Cloud for
   any reason, just delete the `shap==0.46.0` line from `requirements.txt`
   - nothing else needs to change, the app detects its absence and uses the
   fallback.**
3. **A running prediction log**, written to `logs/predictions_log.csv` next
   to the app, that every batch gets appended to. This powers both:
   - **Investigate Asset**: trend charts for any `component_id` across
     however many batches have been run against it.
   - **Model Performance**: usage stats, and an optional upload of real
     outcomes (`actual_maintenance_type`, `actual_failure_risk_score`,
     `actual_remaining_useful_life_days`, matched on `component_id` +
     `snapshot_date`) to compute realized accuracy/error - i.e. how the
     model is doing on real outcomes, not just the held-out test split from
     training time.

   **This log is ephemeral**: it lives on the running container's disk and
   is wiped on redeploy, or when a free-tier app spins back up after going
   to sleep. For a live pitch/demo session that's fine. Two ways to carry
   history further without standing up real infrastructure:
   - Use the download/re-upload button in the **Investigate Asset** tab to
     carry the log between sessions by hand.
   - Before using this on real production data, swap `append_to_log` /
     `read_log` in `pm_logic.py` for calls to a real database (Postgres,
     SQLite on a persistent volume, a Google Sheet, etc.) - they're the only
     two functions that touch the log file, so that's a contained change.
4. **Risk tiers + recommended actions**, not just a raw 0-1 score: Low /
   Medium / High / Critical, each with a one-line recommended action, used
   throughout the app (`pm_logic.risk_tier`, thresholds at 0.30 / 0.55 /
   0.80 - tune these in `pm_logic.py` once real outcome data suggests better
   cutoffs).
5. **Classifier confidence** alongside the predicted maintenance type
   (`predict_proba`), and a **data-drift panel** that compares each upload's
   numeric feature distribution to the training data, flagging anything
   shifted by more than 1 standard deviation.

## Run it locally

```bash
pip install -r requirements.txt
streamlit run app.py
```

First launch will show a "Loading models..." spinner while it pulls the 4
files from Drive (needs internet access); after that they're cached in the
local `models/` folder so it won't re-download on every rerun. It opens at
`http://localhost:8501` - upload `sample_input.csv` to try it immediately, or
any CSV with these columns:

- **Required:** `age_days`, `fault_count_last_30d`, `fault_count_last_90d`,
  `downtime_minutes_last_90d`, `days_since_last_maintenance`,
  `degradation_index`, `comp_type`, `section`, `last_maintenance_type`, `line`
- **Optional:** `component_id`, `area_code`, `component_name`,
  `snapshot_date` (defaults to today if left out) - include `component_id`
  if you want the Investigate Asset tab to be useful, and both
  `component_id` + `snapshot_date` if you plan to score against real
  outcomes later.

Rows don't need to be perfect - see "Input validation" above.

## Deploy it for free (Streamlit Community Cloud)

1. Create a new GitHub repository and push these files - still no large
   files, so the regular GitHub web uploader or a plain `git push` both work
   fine:
   ```bash
   git init
   git add app.py pm_logic.py requirements.txt reference_stats.json metrics_summary.json sample_input.csv
   git commit -m "Predictive maintenance intelligence platform"
   git branch -M main
   git remote add origin https://github.com/<your-username>/<repo-name>.git
   git push -u origin main
   ```
2. Go to **share.streamlit.io**, sign in with GitHub, and click **New app**.
3. Pick the repository, branch (`main`), and main file path (`app.py`).
4. Click **Deploy**. Streamlit Cloud installs `requirements.txt`, the app
   downloads the models from Drive on first boot, and you get a public
   `https://<something>.streamlit.app` URL to share or open in your pitch.
5. Any time you push a new commit, the app redeploys automatically - **but
   a redeploy wipes the prediction log** (see "What's new" above), so
   download it first from the Investigate Asset tab if you want to keep it.

If your company would rather this not be public once real data is involved,
Streamlit Community Cloud apps can be restricted to specific viewers under
the app's sharing settings, or the app can instead be run on an internal
server with the same two commands under "Run it locally" - and the model
files should move off a public Drive link onto something access-controlled
at that point too.

## Testing

`test_pm_logic.py` exercises every function in `pm_logic.py` - validation on
clean vs. deliberately messy data (unseen categories, out-of-range readings,
missing values, bad types), end-to-end predictions, explanations, drift
detection, and the prediction log - directly against the **real trained
models**, not mocks. It doesn't need Streamlit at all:

```bash
pip install -r requirements.txt
python3 test_pm_logic.py
```

Worth rerunning after any retrain or logic change, especially once real data
replaces the synthetic set - it's the fastest way to catch a schema mismatch
or a broken edge case before it reaches the deployed app.

## Retraining on real data

`pm_synth/train_models.py` is designed to be rerun unchanged on a real CSV
as long as it has the same column names - point `INPUT_CSV` at the new file
and run it. It now regenerates **both** things the app needs:

- the 4 `.joblib` models (re-upload these to Google Drive and swap their
  file IDs into `MODEL_FILES` in `app.py`, same as before)
- `reference_stats.json` (small - just commit the new version straight into
  the repo, no Drive upload needed)

`metrics_summary.json` is also regenerated automatically and can be
committed the same way, so the Model Performance tab's training-time
numbers stay current with whatever the model was last trained on.
